## Задание 2. Разработка и заполнение проверочного листа для бизнес-систем

## Анализ ситуации и выбор разделов для проверочного листа

### **Идентифицированные системы и их критичность с точки зрения безопасности**

| Система                    | Тип данных                                                           | Ключевые риски                                    |
|----------------------------|----------------------------------------------------------------------|---------------------------------------------------|
| **Витрина продаж**         | ПДн клиентов (ФИО, телефон, email, паспортные данные)                | Утечка ПДн, подмена данных бронирования           |
| **CRM (клиентская)**       | Полный профиль клиента, история сделок                               | Несанкционированный доступ, изменение данных      |
| **Онлайн-тур**             | Данные осмотра, возможно, фото/видео                                 | Доступ к чужим данным                             |
| **Онлайн-сделка**          | Паспортные данные, данные госорганов, юридически значимая информация | Критический – компрометация сделок                |
| **CRM ЖКУ**                | Данные собственников, адреса, платёжная информация                   | Утечка персональных и платёжных данных            |
| **Бухгалтерская система**  | Финансовые данные, банковские реквизиты                              | Финансовое мошенничество                          |
| **Active Directory**       | Учётные записи, права доступа                                        | Компрометация всей инфраструктуры                 |
| **Платёжные системы**      | Данные банковских карт, платёжные поручения                          | PCI DSS, финансовые риски                         |
| **Поставщик ресурсов ЖКХ** | Данные о потреблении, начислениях                                    | Целостность данных, несанкционированное изменение |
| **Хранилище данных / BI**  | Агрегированные данные всех систем                                    | Массовая утечка, нецелевое использование          |

### **Обоснование выбора разделов проверочного листа**

На основе описанных проблем бизнеса я выбираю следующие разделы:

## Обоснование выбора разделов

### Раздел I. Управление доступом – **ВЫСОКИЙ ПРИОРИТЕТ**
Компания явно указывает проблему: «несколько точек регистрации нового клиента, координации нет», «ограничения по передаваемым данным обусловлены бизнес-процессами, а не системно». Это прямо говорит об отсутствии централизованного управления доступом. Плюс упоминание Active Directory как отдельного элемента на схеме.
- **Управление доступом** – критично, так как выявлены проблемы: точки регистрации не скоординированы, нет контроля потоков данных между системами, API партнёров дают избыточные права

### Раздел II. Безопасность данных – **ВЫСОКИЙ ПРИОРИТЕТ**
Ключевые проблемы: клиенты видят чужие данные, нет ограничений на доступ к данным со стороны систем обработки, компания не может развивать направление обработки данных. Это указывает на отсутствие Data Governance и контроля доступа к данным.
- **Безопасность данных** – основная проблема бизнеса: нет системного контроля данных, смешиваются данные разных клиентов, планируется развитие на базе данных

### Раздел III. Защита инфраструктуры – **СРЕДНИЙ ПРИОРИТЕТ**
Выбран, так как компания использует гибридную инфраструктуру (собственный ЦОД + облако), есть интеграции с партнёрами через API. Firewall уже упомянут, но требуется более детальная проверка.
- **Защита инфраструктуры** – частично (интеграции, API партнёров требуют контроля)

### Раздел IV. Управление инцидентами – **СРЕДНИЙ ПРИОРИТЕТ**
Бизнес обеспокоен утечкой у конкурента и хочет предотвратить подобное. Есть жалобы клиентов на ошибки в личном кабинете – это потенциальные инциденты, которые нужно расследовать. Необходима проверка процессов реагирования.
- **Управление инцидентами** – частично (реагирование на риски утечек, соответствие законодательству)
 
### Раздел V. Специфические аспекты – **НИЗКИЙ ПРИОРИТЕТ для текущего аудита**
Включён по шаблону, но для текущих проблем компании имеет второстепенное значение. Основной фокус – на управлении доступом, безопасности данных и интеграциях.
- **Специфические аспекты** - оставляем

### Раздел VI. Интеграционная безопасность (API и партнёры) – **ВЫСОКИЙ ПРИОРИТЕТ**
Этот раздел добавлен отдельно, так как в описании явно указано:
- Контракты API содержат категории данных, предоставляющие ПДн.
- Некоторые контракты позволяют внешним пользователям выполнять действия и получать данные, к которым у них не должно быть доступа.
- Нет единых политик безопасности и системного контроля за передаваемыми данными.

Это критическая проблема, требующая немедленного аудита.
- **Интеграционная безопасность** – добавляю отдельным блоком, так как основная проблема – неконтролируемые интеграции с партнёрами

## Задание 3. Внешние интеграции

PropDevelopment хочет расширить бизнес-функции для собственников и жильцов. Компания планирует добавить в систему новые сервисы «Умный дом». Эти сервисы готов предоставить партнёр.

Вы согласовали техническое задание с бизнесом и выбрали две услуги для внедрения:
- Интеллектуальный домофон. Включает функции классического видеодомофона — открытие по звонку. Также есть возможность распознавать пользователей по биометрии (по лицу) и автоматически открывать дверь, если им разрешён доступ в дом.
- Интеллектуальный шлагбаум. Включает функции классического управления шлагбаумом и автоматически открывает доступ, если распознаёт номера автомобилей, которым въезд разрешён.

Новые сервисы должны быть доступны через текущее мобильное приложение, которое используют собственники.

## 3. Список требований к внешним интеграциям

### 3.1. Требования к безопасности

| №      | Требование                                                                                                                                                                            | Обоснование                                                                              |
|--------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------|
| **Б1** | Все интеграции должны использовать **TLS 1.3** (допускается TLS 1.2 с отключением устаревших шифров).                                                                                 | Защита данных в транзите (биометрические шаблоны, номера авто, логи доступа).            |
| **Б2** | Биометрические данные (слепки лиц) не должны передаваться за пределы партнёрской платформы. Идентификатор пользователя и биометрический идентификатор должны быть псевдонимизированы. | Соответствие 152-ФЗ (биометрия – специальная категория ПДн).                             |
| **Б3** | Все события доступа (открытие двери, подъём шлагбаума) должны логироваться в центральной системе PropDevelopment с сохранением как минимум 3 лет.                                     | Аудит безопасности, расследование инцидентов.                                            |
| **Б4** | Партнёр не должен иметь возможности изменять права доступа пользователей напрямую. Только PropDevelopment является источником истины (Source of Truth) для правил доступа.            | Принцип минимальных привилегий, исключение несанкционированного изменения.               |
| **Б5** | При интеграции использовать **модель «только в исходящем направлении»**: PropDevelopment инициирует соединение к API партнёра, но не наоборот.                                        | Снижение поверхности атаки, отсутствие открытых портов в инфраструктуре PropDevelopment. |
| **Б6** | Логирование всех API-вызовов (включая метаданные, но без чувствительных данных) должно вестись с двух сторон.                                                                         | Возможность расследования при сбоях и инцидентах.                                        |
| **Б7** | Партнёр должен проходить ежегодный аудит безопасности и предоставлять документацию по защите ПДн.                                                                                     | Управление рисками сторонних поставщиков.                                                |

### 3.2. Протоколы аутентификации и авторизации

| Компонент                                                                      | Протокол                                        | Детали                                                                                                                |
|--------------------------------------------------------------------------------|-------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------|
| **Мобильное приложение → API Gateway**                                         | OAuth 2.0 + JWT                                 | Токен доступа (access token) с ограниченным временем жизни. Refresh token для продления.                              |
| **API Gateway → микросервисы**                                                 | JWT или mTLS                                    | Внутренний контур – передача контекста пользователя через JWT.                                                        |
| **PropDevelopment → Партнёрский API**                                          | **OAuth 2.0 (Client Credentials)**              | Машинное взаимодействие без участия пользователя. Client ID + Client Secret + TLS.                                    |
| **Партнёрская платформа → PropDevelopment (callback)**                         | **mTLS + статический API‑ключ**                 | Для событий, которые партнёр может инициировать (например, «человек прошёл по биометрии»). Домены должны быть белыми. |
| **Партнёрские внутренние сервисы**                                             | **gRPC + mTLS** или HTTP Basic (защищённый TLS) | Внутри контура партнёра – для микросервисного взаимодействия.                                                         |
| **Мобильное приложение – прямое взаимодействие с устройством (шлюз партнёра)** | **WebSocket + токен, выданный PropDevelopment** | Кратковременный токен действует 60 секунд для выполнения одной операции (открыть дверь).                              |

### 3.3. Организация взаимодействия между системами

#### 3.3.1. Сценарий «Регистрация умного устройства»

1. Сотрудник УК добавляет устройство через веб-интерфейс PropDevelopment.
2. `device-manager-service` вызывает API партнёра `POST /devices` с серийным номером и типом.
3. Партнёр возвращает `device_id` и `device_secret`, который сохраняется в `device-db`.
4. Устройство активируется на стороне партнёра и связывается с жилым комплексом.

#### 3.3.2. Сценарий «Настройка прав доступа для жителя»

1. Собственник через мобильное приложение загружает/удаляет биометрический шаблон.
2. Мобильное приложение отправляет запрос в `access-management-service`.
3. Сервис валидирует права (например, собственник ли он этой квартиры).
4. После валидации `device-manager-service` вызывает API партнёра:
   ```http
   PUT /devices/{device_id}/biometrics
   Authorization: Bearer <service_token>
   Content-Type: application/json
   ```
   Тело: `{"user_ref": "<псевдоним>", "biometric_template": "<хэш/ссылка>"}`.
5. Партнёр сохраняет привязку и возвращает статус.

#### 3.3.3. Сценарий «Автоматическое открытие шлагбаума по номеру автомобиля»

1. Камера партнёра распознаёт номер.
2. Партнёр вызывает защищённый callback URL PropDevelopment:
   `POST /api/integration/access/check`
   с заголовком `X-API-Key` и телом `{"plate": "A123BC777", "device_id": "..."}`.
3. `api-gateway` проверяет API-ключ, маршрутизирует запрос в `access-management-service`.
4. Сервис проверяет:
    - Разрешён ли номер в системе.
    - Связан ли номер с активным доступом (например, пропуск действует).
5. Возвращает решение: `{"access": "granted", "reason": "resident"}` или `"denied"`.
6. Партнёр выполняет соответствующее действие: открывает шлагбаум или отказывает.

#### 3.3.4. Синхронизация прав и кэширование

- `access-management-service` хранит права доступа в своей БД (`access-db`).
- Партнёр **не хранит права** – каждый запрос доступа проверяется в PropDevelopment.
- Допускается кратковременное кэширование решения (не более 5 минут) для снижения нагрузки, но нужно уведомление об отзыве прав.

#### 3.3.5. Обработка недоступности партнёра

- При недоступности API партнёра `device-manager-service`:
    - Переходит в **offline-режим**, используя кэшированные данные (последний известный статус устройства).
    - Буферизирует команды (например, `open_door`) с использованием механизма retry (3 попытки с экспоненциальной задержкой).
- По восстановлении связи – отправка накопленных команд в хронологическом порядке.

### 3.4. Дополнительные нефункциональные требования

| Параметр                                   | Значение                            |
|--------------------------------------------|-------------------------------------|
| **Максимальное время ответа API партнёра** | ≤ 500 мс (p99) для проверки доступа |
| **Доступность API партнёра**               | ≥ 99.9% (в часы пик)                |
| **Срок хранения логов событий доступа**    | 3 года                              |
| **Время восстановления после сбоя**        | ≤ 15 минут                          |
| **Частота синхронизации справочников**     | Real-time (через Kafka events)      |
